# Taskcraft 最小 Evals

## Goal

用一个简单、可扩展的框架验证 Agent 使用 tc 的正常交付、冷启动恢复和审查修复。以自动评分发现问题，首版不设发布门槛或宣称统计稳定性。

## Approval and scope

用户在本会话确认简化方案：3 个任务、code/model 两种 grader、一份结果报告；暂不加入 L3、无 tc 对照、百分制或加权总分。授权实现，日常评分不依赖人工。

- R1：实现小功能、执行中断后新会话继续、审查带已知缺陷的实现并修复。三个案例复用小型 Node CSV 项目。
- R2：code grader 运行独立验收，检查实际功能与必要 tc 任务记录。模型报告不能覆盖明确的代码失败。
- R3：model grader 在独立上下文中按固定条目检查遗漏要求、越界修改、夸大完成；输出 pass/fail/inconclusive、简短理由及证据引用。证据不足不伪造通过。
- R4：案例结论只有 pass/fail/inconclusive。耗时、调用数单列，未知值不当作零。服务不可用、grader 错误和未建立检查点明确记录；已经可靠取得的失败证据不得被后续基础设施错误抹掉。
- R5：所有正式资产集中在 `evals/`，只有必要的 cases 与生成结果目录。独立入口不依赖 Trellis；暂时规划文件按当前开发流程管理。
- R6：恢复用真实独立会话，禁止把主会话、评分答案或前一会话历史注入被测模型。控制程序必须证明中断检查点成立；未成立不宣称恢复已测。
- R7：需求明确公开，验收实现留在控制侧。模型 grader 不执行被评材料中的指令。测试产物位于临时仓库，保护现有开发改动。

## Implementation choices within approved scope

首个宿主采用本机 Claude Code CLI，默认沿用宿主模型设置，允许显式指定被测模型和 judge 模型。宿主调用失败不自动切换 provider/model。首版无需支持全部宿主；这不影响 Taskcraft 产品的双宿主合同。正常开发及验收运行经 pnpm 脚本启动，不使用 tc 的 done 作为测评自身成功的唯一依据。

## Acceptance

- AC1 / R1,R5：一个入口可列出三个案例、选择运行并输出 JSON 结果及简短可读报告。
- AC2 / R2,R3,R4：代码失败不可被 judge 判优覆盖；无效 judge 输出、API 错误及缺失检查点均可见；单元测试覆盖这些判定分支。
- AC3 / R6：恢复前后会话独立，检查点含 execute 运行状态和真实源码变化，保存中断及恢复依据。没有检查点时恢复结论为 inconclusive。
- AC4 / R2,R7：独立验收在基线/植入缺陷时失败，在已知正确实现时通过，不能只测试框架自己的结构。
- AC5 / R5：使用说明、case、grader、结果在 evals 中集中管理；新增普通案例不需要改写 runner 核心。
- AC6：运行针对性测试、typecheck、lint、format 检查；尝试真实 Agent + model grader smoke 并如实交付结果。真实服务被阻塞时可交付已验证的框架，但必须明确真实链路尚未验证，不能把 mock 当成真实通过。

## Evidence and boundaries

- `package.json`：Node 24、TypeScript、pnpm、Vitest，无已有独立 eval runner。
- `tests/helpers/fake-host.ts`：adapter 自动测试为 mock，不代表真实 Agent 行为。
- `development/evaluations/claude-entry-l2-recovery-2026-09-09.md:7`：先前真实尝试受宿主/模型环境阻塞，L2 恢复未发生；`:73` 起的 CSV 需求可复用，历史临时脚本已删除。
- `src/core/reducer/node-brief.ts:28`：可据此验证实际恢复所需上下文，不预设产品通过。
- `development/specs/architecture.md:25`：Taskcraft 不调度宿主。Evals 是开发工具，不修改产品 Command service 边界。

## 独立看板扩展（已确认）

用户认为逐份 Markdown 阅读、寻找失败原因和手工比较历史效率过低，要求直观看板：知道测了哪些内容、何时测、相较过去进步或退步，并能从概览深入查看细节。

- R8：中文概览按三个测评场景组织，即使从未运行也显示该场景；可看到最近尝试时间、当前结果及一句话原因。
- R9：同一入口浏览每次历史记录、点开具体检查和依据，无需用户自行寻找 Markdown 文件；原始 JSON/Markdown 保留作为附属证据。
- R10：提供本次与历史测评的结果变化和耗时差异。无法判定、环境/执行阻塞不能当作功能退步；没有可比历史时明确显示暂无对比。比较需要固定场景/验收口径与模型条件，不能从一个旧报告猜测版本。
- R11：前置执行未成立时，详情先展示运行中断/受阻原因，将依赖前置的缺产物/缺记录显示为无法判定；不把同一阻塞展开成多项独立功能失败。原始观察保留且可展开，不改写历史原始报告。
- R12：继续保持目录集中和简单框架，暂不新增批量调度、Web 上启动模型、账号或远端存储。
- R13：用户指出场景背景、具体任务与成功标准不可省略。列表用中文交代具体工作；详情提供背景、tc 能力目标、任务要求、输入输出示例、执行步骤、覆盖范围与完整验收标准，可折叠但未运行时也可读取。逐项结果显示中文名称、通过标准、检查方式和证据；区分当前定义与历史报告，不把实际结果条数当作标准总数。刷新保持展开状态与滚动位置。

新增验收候选：加载现有 delivery 报告时，首页显示一条受阻尝试、两个未测场景，不能显示多个功能缺陷；补充历史 fixture 验证改善/退步/持平/不可比，并做桌面和窄屏实际页面 smoke。历史报告缺少比较元数据时仍可读，标注不可直接比较；今后运行记录补齐比较所需来源信息。

用户已确认采用独立 Evals 看板，并明确架构边界：Evals 属于 evaluation harness；tc Watch 属于 agent harness，不建立关联。按上一轮概览、历史、对比、详情方案实施。页面、服务及报告读取集中在 evals/，不导入/复用 watch/ 或 src/watch/，不访问产品 Task Store，不增加 tc Watch 导航或 API。正式入口为 `pnpm eval --watch`，浏览的是已有 JSON 报告；浏览页面不启动被测 Agent，也不需要 tc init。

明确验收：现有唯一历史记录显示受阻、两个未测场景；旧报告可读且明确缺少可比元数据；比较条件一致的历史 fixture 可展示改善、退步、持平及逐项差异；运行阻塞不统计为多次功能失败；桌面/移动页面可点开历史详情并自动读取新增报告。界面全中文、以结论优先，原始诊断折叠。

## Out of scope

L3、A/B 对照、大型评分平台、分布式运行、排行榜、自动阈值发布门、复杂插件、固定人工评分步骤、自动修复测评发现的产品问题。历史报告可被只读看板消费，但不覆盖或伪造原始结果。
