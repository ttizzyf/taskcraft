# Taskcraft 功能地图

一页看清 tc **现在能干什么**、**还不能干什么**、**东西在哪**。

- 状态以 `node dist/cli.js --help` 和 `src/` 里的代码为准（本文写于 2026-09-26）。
- 文档里写了但代码里没有的，本文一律标成「还没做」。
- 本文只是导航。真正的规则以 [`README.md`](README.md) 里的权威顺序为准。

---

## 0. 先说人话：这东西到底在干什么

Taskcraft 是给 AI 用的任务台账。

AI 干一件活的时候，会把「干了什么、干到哪、凭什么说干完了」记进一个本地数据库。
这个数据库是**唯一的事实来源**——所有记录都从这一个口子写进去，别的地方只能读。
你在浏览器里看到的看板，和 AI 在命令行里看到的进度，都是从同一份记录算出来的，
不存在"看板显示的和实际不一样"。

```
AI（Codex / Claude）──命令行──> 写入口 ──> 本地数据库 taskcraft.db
                                    │
你 ──浏览器看板 / 命令行──────────────> 只读算出来 <──┘
```

## 1. 黑话对照表

看代码或旧文档前先扫一眼，后面正文会尽量说人话。

| 文档里的词 | 人话 |
| --- | --- |
| Task / 任务 | 一件要干的活 |
| Node / 节点 | 干活的一个步骤，比如"先定目标""再执行""最后记录" |
| Attempt / attempt | 某个步骤的**一次**尝试（重做就是新的一次） |
| Obligation | 这件事**必须交付什么**才算数（分必做 / 建议做 / 可选做） |
| Revision / 版本 | 任务的第几版方案。改方案就是出新版，旧版不删 |
| Spec | 项目里的规范文档（写在 Git 里的 Markdown） |
| Binding / 绑定 | 这件活**要用哪几份规范**，开工前先钉死 |
| Drift / 漂移 | 开工后规范被人改了，和钉死的时候**对不上**了 |
| Spec Impact | 干完活要回答一句："这次有没有产生新规矩？" |
| Reducer | 唯一的写入口（所有记录都由它写） |
| Projector | 只读的状态推算器（把记录翻译成"现在什么状态"） |
| Evidence | 证据。测试结果、报告、日志这类能证明"我真做了"的东西 |
| Blocker | 卡住了。而且必须说明**卡在哪、缺什么、谁来补** |
| CAS / expected-revision | 版本校验。写之前先对一下版本号，防止两边打架 |
| deferred | 文档里写了，但**代码还没做**，用不了 |
| Gate / 门禁 | 前置检查。不过关就不让往下走 |
| Adapter | 对接层。负责和 Codex / Claude 这些宿主软件打交道 |
| Entry Hook | 开机钩子。你一发消息，它先偷偷看一眼要不要接管 |
| Watch | 浏览器看板 |
| Doctor | 体检命令，只读，查数据有没有坏 |

## 2. 命令：能用的 vs 不能用的

### 2.1 能用的（帮助里查得到）

一共 12 个：

| 命令 | 干什么 |
| --- | --- |
| `tc init` | 建数据库；可选顺手装开机钩子 |
| `tc enable off\|ask\|always` | 设置接管模式 |
| `tc agent capabilities` | 看看这台机器上的宿主支持什么 |
| `tc agent test-entry-hook` | 真跑一次开机钩子，看它到底能不能用 |
| `tc doctor` | 体检，只读 |
| `tc spec list\|check\|resolve` | 看规范清单 |
| `tc task new\|list\|show\|next\|cancel\|wait\|resume\|fact add\|spec refresh` | 管任务 |
| `tc run <task>` | **开工**：激活任务并领一个步骤 |
| `tc run complete\|fail\|retry\|attach\|status` | 交结果 / 报失败 / 重做 / 关联宿主 / 看进度 |
| `tc review start\|pass\|changes\|replan` | 审查相关的四条命令 |
| `tc status` | 现在什么状态，下一步该敲什么 |
| `tc state --breadcrumb` | 给开机钩子用的简短状态 |
| `tc watch` | 开浏览器看板 |
| `tc`（不带参数） | 只有一个任务在跑时，直接告诉你下一步 |

所有命令都支持 `--json`。写命令支持 `--expected-revision`（对版本号）。
出错一定非零退出，并给一个稳定的错误码。

### 2.2 还不能用的（文档写了，但敲了会报错）

| 敲不了的 | 写在哪 |
| --- | --- |
| `tc lifecycle ...` | `cli.md` §2、§6 |
| `tc explain <错误码>` | `cli.md` §2 |
| `tc task promote` / `tc task revise` | `cli.md` §4 |
| `tc task evidence add` / `tc task export` | `cli.md` §4 |
| `--dry-run` / `--no-color` / 补全脚本 | `cli.md` §1、§10 |
| `run status --follow` | `cli.md` §10，代码里没实现 |

> ⚠️ **最容易踩的坑：证据不能单独提交。**
> 它是跟着 `tc run complete` 的结果一起写进去的。
> `tc task evidence add` 是没做的，别照着旧笔记去敲。

### 2.3 忘了命令怎么写？

别翻文档，直接问命令本身：

```bash
node dist/cli.js <命令> --help        # 任何一层都能问
node dist/cli.js task next T-1 --json # 直接告诉你下一步敲什么
```

`task next`、`status`、开机钩子的输出**本身就会给出下一条该敲的命令**——
这是故意的，就是不想让你去翻文档。

## 3. 四个核心概念

### 3.1 记录分三层

| 层 | 装什么 | 特点 |
| --- | --- | --- |
| **方案层** | 这件活分几步、每步要交什么 | **只加不改**，改方案就出新版 |
| **过程层** | 什么时候开的工、每步试了几次、结果如何、证据、卡在哪 | 边干边写 |
| **观察层** | 宿主软件自己报的：还在跑吗、多久没动静了、花了多少 token | **只用来诊断**，不影响任务本身 |

关键区分：**观察层改了不算数**。要改任务的真实状态，必须走写入口。

### 3.2 状态有五个

数据库里**不存**"现在什么状态"这个字段，它是算出来的：

| 状态 | 什么意思 |
| --- | --- |
| `queued` | 建了卡，还没开工 |
| `active` | 正在干 |
| `waiting` | 卡住了，**一定会说明卡在哪** |
| `done` | 干完了（该交的都交了） |
| `cancelled` | 取消了 |

卡住的原因只有四种：`needs_input`（等你说话）、`needs_decision`（等你拍板）、
`blocked_dependency`（等别的活）、`failed_retries_exhausted`（重试次数用完了）。

取消优先级最高。另外：**大任务拆小任务不会多出第六种状态**——
小任务被取消了，大任务就变成"卡住了，等你拍板"。

### 3.3 步骤有六种

| 步骤 | 什么时候出现 | 交出什么 |
| --- | --- | --- |
| `frame` | 目标不清楚时 | 目标、范围、验收标准、不做什么 |
| `plan` | 需要拆活时 | 拆成哪几块、谁依赖谁、怎么合起来 |
| `execute` | 所有任务都有 | 干出来的东西 + 验证证据 |
| `review` | 中大型任务必做，小任务可选 | 通过 / 提意见 |
| `integrate` | 多块活要合成一个时 | 合起来的验收证据 |
| `record` | 所有任务都有 | 最终结论、遗留风险、**规范影响** |

以后可能还会加 `research`（调研）、`security-review`（安全审查）这类。

### 3.4 交付要求分三档

| 档 | 能不能卡住你 | 能不能跳过 |
| --- | --- | --- |
| **必做** | **能** | 不能。而且必须有证据才算数 |
| **建议做** | 不能 | 能，但要记一句为什么跳 |
| **可选** | 不能 | 能 |

## 4. 三条流程

### L1：小活（局部、可逆、不碰边界）

```
execute  →  record        （review 可选）
```

敲法：`tc task new --level 1` → `tc run T-1` → `tc run complete T-1 --result result.json`

### L2：一般活（默认）

```
frame → execute → review → record
```

`review` 必须是**单独一次**，不能自己干完自己签字了事。

### L3：大活（跨模块 / 要拆活 / 要拍板 / 不可逆）

分两段走：

```
第一段（定方案）：
  frame → plan → 可行性审查

第二段（动手），二选一：
  拆成几块：  真实的小任务 ×N  →  integrate  →  record
  不拆：      execute → delivery 审查 → integrate → record
```

**L3 的硬规矩：**

- 只能拆**一层**。小任务不能再往下拆，也不许有"大任务里套大任务"。
- 拆活至少拆 **2 块**。方案通过的那一刻，小任务会被**一次性全建出来**，
  哪一步失败就整体回滚，不会建一半。
- 实在拆不动才允许"不拆"，但方案里**必须写明至少试过一次、为什么失败**。
- 小任务不重复"定目标/做计划"，它第一个动作就是 `execute`。
- **tc 不负责派活、不负责停活、也不管调度。** 只有你显式写了"A 依赖 B"才会真卡住；
  "范围"只是提醒，不是红线。

### 4.1 审查发现问题后怎么走

| 敲什么 | 什么时候用 | 后果 |
| --- | --- | --- |
| `review pass` | 通过 | 审查者自己顺手改过也行，但要留证据 |
| `review changes` | 小问题，方案不变 | 当前这版里**再试一次** |
| `review replan` | 方案本身要改 | **出新版方案**；旧的小任务标记成"不再需要"，**但不删不取消** |

审查还要如实交代两件事：**这次审查是怎么关联上的**（只看上下文 / 手动关联 / 宿主自动关联），
以及**审查的人是不是干活的同一个人**。同一个人也可以，但必须写明。

## 5. 规范（Spec）系统

**核心一句话：规范正文就是 Git 里的 Markdown，数据库只记"是哪份文件、内容指纹是什么"，不复制正文。**

### 5.1 三条只读命令

```bash
tc spec list                                     # 列出所有规范 + 内容指纹
tc spec check                                    # 全面检查清单和文件有没有问题
tc spec resolve --path src/core/reducer.ts       # 改了这个文件，该看哪些规范？
```

`resolve` **只给候选，不替你决定**。

### 5.2 开工前钉死"用哪几份规范"

不同级别，钉死的时机不一样：

- **L1**：建卡时就把选好的规范钉到"执行"和"记录"两步上。
- **L2**：建卡时只钉给"定目标"这一步；等"定目标"出了结果，再钉到后面几步。
- **L3**：方案通过时，一次性把大任务和各小任务的规范全钉好。

**开工前会核对**：规范还在不在、内容变没变。

| 情况 | 怎么办 |
| --- | --- |
| **必用**的规范内容变了 | 直接报错，**不让开工** |
| **建议用**的规范内容变了 | 只在界面上提示一下，不拦 |

`tc task spec refresh` 只会**出新版方案 + 新快照**，不会偷偷改掉旧的钉法。

### 5.3 干完活要回答一句

新版的任务，交结果时**必须回答**："这次有没有产生新规矩？"

| 回答 | 要求 |
| --- | --- |
| 没有 | 写清楚理由 |
| 有，已更新 | 得指出更新了哪份规范，还要有本次的证据 |
| 有，待定 | 提个候选给负责人拍板。**不会自动写进规范** |

这三样（结果、证据、影响说明）是**一次性写进去的**，不会写一半。
老任务不受影响，按老规矩走完就行。

## 6. 和 Codex / Claude 怎么接

### 6.1 开机钩子：默认闭嘴

你每发一条消息，钩子先偷偷看一眼：

```
你发消息
   ↓
装了 tc 吗？ —— 没装 → 什么都不做
   ↓ 装了
接管关了吗？ —— 关了 → 什么都不做
   ↓ 开着
有任务在跑吗？ —— 有 → 塞一句"当前进度 + 下一步"
   ↓ 没有
这活需要记账吗？ —— 不需要 / 拿不准 → 什么都不做
   ↓ 需要
问一次要不要建卡（ask 模式）／ 直接建草稿（always 模式）
```

**关键：普通聊天、随便问问、拿不准的，它一个字都不输出。**
这是刻意的设计——不想让你觉得有个东西一直在旁边插嘴。

### 6.2 对接层

- 目前只做了 **Codex** 和 **Claude** 两家。别家的会明确报"不支持"，不会假装能用。
- 装在哪：Codex 是 `.codex/hooks.json`，Claude 是 `.claude/settings.json`。
- **会同时写两份脚本**：Linux/macOS 用 `bash` 那份，Windows 用 `node` 那份
  （Windows 上跑钩子没有 bash）。
- Codex 那边，"信任项目"**不等于**"信任这个钩子"。钩子改了之后，
  **还得你去 `/hooks` 里点一下确认**。`test-entry-hook` **不会帮你绕过**这一步。

## 7. 看板与体检

### 7.1 看板有四个页面

| 页面 | 看什么 |
| --- | --- |
| **总览** | 所有任务的标题、级别、状态、当前步骤、做到几成、卡在哪、下一步 |
| **详情** | 目标/范围/验收、为什么定这个级别、步骤图、每步要交什么、证据、审查意见、时间线 |
| **运行** | 宿主软件跑得怎么样、多久没动静、开机钩子上次测的结果 |
| **诊断** | 只有出问题时才显示 |

总览默认按 `进行中 / 卡住 / 待开工 / 已完成 / 已取消` 分组。

### 7.2 看板背后的接口

`/api/board`、`/api/runtime`、`/api/diagnostics`。**全是只读**，
直接拿算好的状态，看板自己不做第二套计算，也不写数据库。

### 7.3 体检（`tc doctor`）

查这些：数据库结构版本、外键、孤儿记录、事件连不连续、方案指纹、
大任务的层级/覆盖/依赖、规范清单和绑定有没有对不上、状态能不能重建、开机钩子的数据格式。

**只读**，只告诉你哪里有问题。

## 8. 测评框架

用来测"AI 用 tc 干活靠不靠谱"，属于开发工具，不是产品本身。

```bash
pnpm eval --list                 # 看有哪些案例
pnpm eval --case delivery        # 正常交付
pnpm eval --case recovery        # 断了之后能不能接上
pnpm eval --case review          # 审查发现问题后能不能改对
pnpm eval --watch                # 开个看板看结果
```

每次跑都在**系统临时目录**建一个干净工作区（故意放在项目外，
免得继承本仓库的配置），结果写到 `evals/runs/`。

### 10.3 tc 比起 Trellis 缺什么

tc 有清单、有绑定、有检查、有影响说明，但**不会自动塞给 AI，也没有"写回规范"的命令**。

## 11. 三条最容易忘的规矩

1. **`task new` 只是建卡，不开工。** 真正开工是第一次 `tc run`，它才会写"已开工"并领第一步。
2. **证据不能单独提交。** 跟着 `tc run complete` 的结果一起写。
3. **写命令都要带版本号**（`--expected-revision`，不带就从 `tc status --json` 里拿）。
   对不上会报错，并告诉你怎么重读。
